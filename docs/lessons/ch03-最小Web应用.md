# 第 3 章 最小 Web 应用：FastAPI 后端 + 单页聊天前端

> 本章目标：把第 2 章的"命令行脚本"升级成第 1 章链路图里的 ②③ 环节——一个能在浏览器里用的 AI 客服。
> 被测系统（SUT, System Under Test）从本章起正式成型，第 6/7 章就测它。

## 1. 本章新增概念（配例子）

### 后端 API（POST /chat）
后端就是"一个常驻运行、等待别人来调用的程序"。它对外开一个"窗口"叫**接口（endpoint）**。
本项目只有一个核心接口：`POST /chat`。前端把用户的话发给它，它把 AI 的回答还回去。
例子：`curl -X POST http://127.0.0.1:8000/chat -d '{"message":"能退款吗"}'` 就是"手动当一次前端"。

### 请求/响应模型（Pydantic）
`ChatRequest(BaseModel)` 规定了 `/chat` 只接受长这样的数据：必须有个字符串字段 `message`。
不符合的会被 FastAPI **自动拦截**并返回 422，根本进不到业务代码。
例子：发 `{}`（缺 message）→ 直接 422。这就是"输入校验"，第 6 章会专门测它。

### 静态页面与前后端通信（fetch）
`GET /` 返回 `index.html`。浏览器加载这个 HTML，里面的 JS 用 `fetch("/chat", {...})`
在用户点"发送"时向后端发请求。**前端不碰大模型，只跟自己的后端说话**——
这样 API Key 藏在后端，不会泄露到浏览器里（安全设计，也是第 6 章的一个测试视角）。

## 2. 本项目代码结构

```
app/
├── hello_deepseek.py     ← 第2章：命令行直连（保留作对照）
├── main.py               ← 第3章：FastAPI 后端
├── static/index.html     ← 第3章：聊天前端
└── requirements.txt      ← 依赖：requests + fastapi + uvicorn
```

`main.py` 关键三块：
1. `POST /chat`：收 `{message}` → 拼成第 2 章的 messages 数组 → 调 DeepSeek → 返回 `{reply, usage}`。
2. `GET /`：把 `index.html` 交给浏览器。
3. `SYSTEM_PROMPT`：把"电商客服小D，只答售后"的人设写死在这里（第 4 章会强化）。

## 3. 如何启动

```bash
cd /workspace
set -a && . ./.env && set +a          # 载入 API Key
python3 -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```
浏览器打开 http://127.0.0.1:8000/ 即可对话。

## 4. 实跑验证（本章的"验收测试"）

| 用例 | 输入 | 实际结果 | 结论 |
|---|---|---|---|
| 首页 | `GET /` | 200，`text/html` | 前端正常返回 |

## 5. 一个真实的测试发现（重点体会）

空消息 `{"message":""}` 竟然返回 200，AI 还热情地回了句"请问您遇到什么问题"。
这说明：**Pydantic 只校验"字段存在且是字符串"，不校验"内容非空"**。

- 从"能不能跑"看：不是 bug。
- 从"产品该不该响应空输入"看：这是**缺陷**——正常应拒绝空提问，而不是浪费一次大模型调用（还花了 token 钱）。

这正是测试人员的价值：**区分"程序报错"和"行为不当"**。第 6 章我们会把"空输入应被拒绝"写成一条
失败的测试用例，然后回到 `main.py` 加校验让它通过——体验一次"测试驱动修复"。

## 6. 为测试铺垫

- `POST /chat` 的请求/响应结构 = 第 6 章接口测试的断言对象（`reply` 非空、异常码正确）。
- `index.html` 的输入框/发送按钮/消息区 = 第 7 章 Playwright 的定位目标。
- 空输入这个缺陷 = 第 6 章第一个"会先红后绿"的用例。
