# 第 1 章 全景链路：一个 AI 客服机器人由哪些环节组成

> 本章目标：看懂一条消息如何从"用户在网页敲下一句话"变成"AI 的回答显示在屏幕上"。
> 这条链路上的每个环节，都是第二部分自动化测试的测试点。

## 1. 链路总览

```
用户提问 → 聊天前端网页 → FastAPI 后端 → DeepSeek 大模型
   ①          ②              ③             ④
                ↑____________↑______________↑
                     回答沿原路返回
```

| 环节 | 是什么 | 类比 | 未来的测试点 |
|---|---|---|---|
| ① 用户提问 | 人在输入框敲一句话 | 电话里客户的开场白 | 各种"奇怪输入"：空、超长、表情、乱码 |
| ② 聊天前端 | 一个 HTML 页面，负责显示对话、发送请求 | 电话机 | 第 7 章 E2E 测试：模拟用户点击输入 |
| ③ FastAPI 后端 | 我们的服务器，接收前端请求、调用大模型、返回结果 | 接线员 | 第 6 章接口测试：直接调 API 验证输入输出 |
| ④ DeepSeek 大模型 | 真正"思考"并生成回答的部分 | 接线员脑子里的知识 | 第 8 章效果评估：回答得好不好 |

## 2. 四个核心概念（都配例子）

### LLM（大语言模型）
一个在海量文字上训练出来的程序，核心能力只有一个：**给定一段文字，预测接下来最合理的文字**。
例子：你输入"退款怎么申请？"，它并不是"查数据库"，而是根据训练学到的语言规律，
一个字一个字地把像答案的话"接"出来。所以它有时会一本正经地胡说（术语叫**幻觉**，第 8 章专门测它）。

### API（应用程序接口）
程序之间互相调用的"服务窗口"，规定了：用什么地址、传什么格式的数据、返回什么格式。
例子：我们调用 DeepSeek 就像去窗口办事——`POST https://api.deepseek.com/chat/completions`，
按它要求的 JSON 格式填好表格递进去，它按固定格式把结果给你。
**对测试来说：API 就是被测系统的"标准操作面"，接口测试测的就是这个窗口。**

### Prompt（提示词）
你发给大模型的全部文字，就是 prompt。它分三种角色：
- `system`：人设指令，如"你是电商客服，只回答售后问题"——用户看不见，但模型必须听；
- `user`：用户说的话，如"我买的杯子碎了"；
- `assistant`：模型之前答过的话（用于让它记住上下文）。
例子：同一句"杯子碎了"，system 写"你是客服"和"你是诗人"，会得到完全不同的回答。
**所以 prompt 本身就是需要测试的"配置"——这是 AI 测试独有的科目。**

### Token
大模型不按"字"计费、不按"行"计算，而是按 token——它把文字切成的最小单位。
粗略换算：1 个汉字 ≈ 1~2 个 token，1 个英文单词 ≈ 1 个多 token。
例子："我要退款" 约 4 个 token。模型有上下文窗口上限（如 64K token），
超了就得丢弃最早的对话——这就是第 4 章"多轮上下文"要处理的问题，也是第 8 章测延迟的计量单位。

## 3. 本章小结：为什么测试人员要关心链路

传统 Web 测试：输入确定 → 输出确定 → 断言相等。
AI 客服测试：输入确定 → 输出**不确定**（同一个问题两次回答可能不同）→ 断言策略要变（第 5 章）。

但链路里 ①②③ 三个环节仍然是**确定性**的（前端发没发请求、后端返没返 200），
只有 ④ 是非确定性的。**把不确定的部分隔离到最小，其余照常测**——这是整个第二部分的方法论主线。
