# 第 10 章 迷你 RAG：给客服挂上知识库

> 本章目标：补上"客服没有知识"这个真实缺陷，并学会 RAG 系统的两层测试——
> **检索召回（确定性）** 与 **忠实度（概率性）**。

## 1. 从一个你已经见过的失败说起

第 8 章的实验还记得吗？同一个问题"退款多久到账"问三次，第三次模型编出
"支付宝/微信 1-3 个工作日"——**前两次它自己都说"以银行/渠道为准"**。

为什么会这样？因为我们只给了它一个人设，没给它任何**公司政策**。
它只能靠训练语料里的"一般常识"猜，猜错就是幻觉。

人设里那条"不编造政策、不确定转人工"，本质是**用规则掩盖没有知识库**。

## 2. 三种补法，为什么选 RAG

| 方案 | 做法 | 成本 | 更新政策时 | 可追溯 |
|---|---|---|---|---|
| 微调（fine-tune） | 用政策数据训练模型 | 高（训练+算力） | **要重新训练** | 差 |
| 塞进提示词 | 全文塞进 system prompt | 中（token 贵） | 改 prompt | 一般 |
| **RAG** | 先检索相关片段，再塞进 prompt | 低 | **换文档即可** | **好（能列出引用）** |

政策类知识**变化频繁**（退款时效调整、活动规则），微调完全不划算；全文塞提示词
迟早撞上下文窗口（第 2 章 Q1 讲的 64K）。所以业界默认选 RAG。

## 3. RAG 三段：R → G → A

```
Retrieval   用户问题 → 检索 Top-3 相关文档
Augmentation 把文档片段拼进 prompt（带"只依据资料回答"的约束）
Generation  LLM 基于片段生成回答
```

**测试的重心在 R，不在 A。** 因为：
- 检索是**确定性**的——问 A 必须召回文档 X，可以像传统测试一样精确断言；
- 生成是**概率性**的——只能评估。

如果检索就召回错了，后面 prompt 写得再好也是"基于错误资料的正确回答"。
**所以 RAG 测试的第一步永远是测召回，而不是测回答。**

## 4. 三个设计决策（都有取舍，我说明理由）

### ① 旁路而不是原地改（方案 A）
新增 `POST /chat/rag`，`/chat` 一行不动。
好处：老链路与 51 条老用例零影响；能 A/B 对比"有无知识"的回答差异；将来要合并只是改路由。

### ② 关键词 bigram 而不是向量检索
10 篇文档规模下，bigram 交集排序已经够准；更重要的是**确定性 = 可精确断言**。
上量后再换 embedding，但"召回命中"的测试思路不变。

### ③ 检索为空时直接兜底，不让模型裸答
`retrieve()` 没命中 → 返回"暂未查到相关规定，建议转人工"，**一次模型调用都不发**。
测试里用 `llm.calls == []` 锁住这个行为——**宁可说不知道，也不能无据生成**。

## 5. 代码结构

```
app/kb/policies.json   10 篇政策文档（id/title/content）
app/retrieval.py       bigram 打分 + 排序（同分按 id，保证确定性）
app/rag_service.py     检索 → 拼【资料】→ 调同一个 LLMClient
app/main.py            新增 POST /chat/rag（复用鉴权/限流 guard）
```

回答里会带 `sources: ["refund", "cancel"]`——**引用可追溯**，这是 RAG 相对于纯生成最大
的工程价值，也是测试的抓手。

## 6. 测试第一层：检索召回（确定性，零成本）

`tests/test_api/test_retrieval.py`，用 `parametrize` 跑 10 个问题 × 2 个指标：

| 指标 | 断言 | 说明 |
|---|---|---|
| Top-1 准确率 | `docs[0]["id"] == expected` | 最严格：第一个就必须对 |
| Top-3 召回率 | `expected in ids[:3]` | 实际系统里进候选集就还有机会 |
| 无命中 | `retrieve("今天天气") == []` | 不能硬凑文档，否则诱发胡编 |
| 确定性 | 两次调用结果完全一致 | 否则无法做回归基线 |
| 排序 | score 单调不增 | 排序逻辑本身也要测 |

**这一类用例一条都不花钱**，所以放在 fast 层，每次提交都跑。

## 7. 测试第二层：忠实度（LLM-as-Judge）

定义：**回答里的每个具体政策，是否都能在检索到的资料里找到依据。**
这是 RAG 最核心的质量指标（业界叫 faithfulness / groundedness）。

实现（`tests/eval/test_rag_quality.py`）：
```
问题 + 检索到的资料 + 模型回答  →  裁判模型  →  {"faithful": bool, "reason": "..."}
聚合：忠实度达标率 >= 80%
```

裁判 rubric 的三条关键规则（写在 `judge.py` 的 FAITHFUL_RUBRIC）：
1. 出现资料外的具体数字/承诺 → 不忠实；
2. 只说"暂未查到、建议转人工" → 视为忠实（安全行为）；
3. 复述资料 → 正常。

### 实跑结果

```
RG01 退款多久能到账  引用 refund,cancel,exchange  忠实
RG02 换货流程是什么  引用 exchange,quality        忠实
RG03 物流三天没更新  引用 shipping                忠实
RG04 运费谁承担      引用 quality,return7         忠实
RG05 保修期多久      引用 warranty,refund         忠实
忠实度达标率 100%（阈值 80%）
```

## 8. 和 ragas / deepeval 的对应关系

| 业界指标（ragas） | 本项目的实现 | 位置 |
|---|---|---|
| `context_recall` | Top-1 / Top-3 召回断言（**更严格**） | test_retrieval.py |
| `faithfulness` | `judge_faithfulness()` | test_rag_quality.py |
| `answer_relevancy` | B 级业务词约束 | test_answers_hit_key_facts |

**为什么没直接 pip install ragas**：它依赖 langchain 全家桶，体量大，且对 Python 3.14
兼容性不稳；为一门课引入 300MB 依赖不划算。本项目的判分接口刻意做成
"问题 + 资料 + 回答"三件套，**形状与 ragas 一致，工作里可以无缝替换**：

```python
from ragas import evaluate
from ragas.metrics import faithfulness, context_recall
# dataset: question / answer / contexts / ground_truth
result = evaluate(dataset, metrics=[faithfulness, context_recall])
```

## 9. 迁移到你的工作（RAG 客服测试 checklist）

拿到一个带知识库的客服系统，按这个顺序测：

1. **知识库本身**：文档是否最新、是否有互相矛盾的两篇（矛盾文档是幻觉之源）
2. **召回**：准备 30~100 条"问题→应命中文档"的标注，测 Top-1/Top-3
3. **兜底**：问库里完全没有的问题，是否明确说"没查到"而不是编
4. **忠实度**：抽 20~50 条真实问题，用裁判或人工核对"回答是否都能在文档里找到"
5. **引用**：回答能否给出出处（产品允许的话）
6. **版本**：知识库更新后，回归第 2 步的召回集
