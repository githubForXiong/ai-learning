# 第 5 章 测试策略总览：AI 应用测试与传统测试有什么不同

> 本章目标：不写一行测试代码，先把"地图"画清楚——AI 应用到底该怎么测、和传统测试差在哪。
> 产出物：`tests/PLAN.md`（本被测系统的完整测试计划），后续 5 章都按它执行。

## 1. 先看一个真实实验（本章最重要的证据）

同一个问题，同一个接口，`temperature=0.3`，连跑 3 次：

| 次数 | 耗时 | 回答长度 | 内容摘要 |
|---|---|---|---|
| 1 | 1.34s | 76 字 | "…一般原路退回需要 1-7 个工作日，**以银行到账为准**" |
| 2 | 1.14s | 80 字 | "…一般原路退回是 1-7 个工作日，**以支付渠道为准**" |
| 3 | 0.68s | 67 字 | "…原路退回：**支付宝/微信通常 1-3 个工作日**，银行…" |

三个事实，一个比一个扎心：

1. **输入相同，输出不同**（三次 md5 全不一样，长度 76/80/67）。这就是**非确定性**。
2. **耗时也不稳定**（1.34s / 1.14s / 0.68s），第 3 次还快得反常。
3. **第 3 次出现了幻觉**——"支付宝/微信 1-3 个工作日"是它编的，前两次都说"以银行/渠道为准"。

如果按传统测试写：`assert reply == "退款需1-7个工作日"`，这条用例**永远红**，而且红得毫无意义。
这就是 AI 测试的第一个分岔点。

## 2. 传统测试 vs AI 测试：一张对照表

| 维度 | 传统 Web 应用 | AI 应用 |
|---|---|---|
| 输出 | 确定：1+1 永远等于 2 | 不确定：同输入可能不同输出 |
| 断言方式 | 精确相等 `==` | 分层：精确 / 范围 / 语义 / 统计 |
| 期望值 | 事先写死 | 常常只能写"应该满足的约束" |
| 失败含义 | 一定是 bug | 可能是 bug，也可能只是"这次措辞不同" |
| 用例稳定性 | 稳定（同环境必同结果） | 天然有 flaky 风险 |
| 测试重点 | 功能正确性 | 功能正确性 **+ 回答质量** |
| 数据 | 依赖数据库 fixture | 依赖 prompt / history / 模型版本 |

**但请注意**：不是"传统测试作废了"，而是**它的地盘缩小了**。被测系统里仍有大片确定性区域（状态码、字段结构、页面元素、payload 拼装），这些照旧用老办法精确断言。

## 3. 核心方法论：把不确定性隔离到最小

整门课贯穿始终的一句话，本章正式提出：

> **凡是能确定的，就精确断言；只有真正不确定的，才交给评估方法。**

落实到本项目的四层（见上方分层图）：

- **L1 单元（完全确定）**：`build_payload()` 输出的 messages 数组、`history[-10:]` 裁剪结果。
  输入 history 是 12 条 → 输出必然是最后 10 条 + system + 本轮 message。**可以 `==` 断言**。
- **L2 接口（大部分确定）**：状态码、响应字段、缺失字段返回 422、上游挂掉返回 502。
  **这些跟大模型说什么无关，精确断言**。只有 `reply` 的内容需要放宽。
- **L3 E2E（行为确定，内容不确定）**：点发送 → 出现用户气泡 → 机器人气泡出现 → 发送按钮恢复可点。
  **流程可精确断言；气泡里的文字用"非空 + 长度"约束**。
- **L4 效果评估（本质不确定）**：回答有没有幻觉、有没有遵守人设。**只能打分、只能统计**。

这个思路的价值：**bug 定位**。如果 L1/L2/L3 全绿、只有 L4 掉分，你知道问题出在"模型/提示词"，
而不是"代码接错了字段"——两层问题性质完全不同，修复的人也完全不同。

## 4. 断言的四级军规（本项目的核心纪律）

| 级别 | 名称 | 什么时候用 | 本项目例子 |
|---|---|---|---|
| A | 硬断言 | 完全确定的字段 | `status_code == 200`、`"reply" in body`、缺失 message → 422 |
| B | 约束断言 | 有边界、内容可变 | `reply != ""`、`len(reply) < 3000`、含"退款/换货"等业务词 |
| C | 软断言 | 语义质量 | 无关话题是否拒答、是否编造政策 |
| D | 统计断言 | 多次运行的指标 | P95 时延 < 5s、拒答率 ≥ 95% |

**为什么必须分级？** 因为一条断言写错级别，整条用例就废了：
- 用 A 去断言 B 的东西（`reply == 固定字符串`）→ 永远红，团队开始无视失败，测试失去意义；
- 用 C 去断言 A 的东西（"状态码对不对"用 AI 打分）→ 又慢又没必要。

## 5. 传统测试技法还能用吗？能，只是对象变了

**等价类划分**仍然适用，只是划分对象从"输入值"变成了"意图场景"：
- 有效等价类：退款类、换货类、物流类、质量类
- 无效等价类：闲聊类、竞品打探类、要求越权类

**边界值分析**对象也变了：
- 字符数边界：`""`（空）、`"a"`（1 字）、2000+ 字
- history 边界：0 条、9 条、10 条、11 条（**正好卡在 `MAX_HISTORY=10` 的裁剪线上**）

**因果图/场景法**：多轮对话天然适合场景法——"先问退款政策，再追问运费谁出"就是一个场景。

新增的、传统测试里没有的维度：
1. **Prompt 维度**：同一输入，改 system prompt 就是不同的"配置"，要回归；
2. **上下文维度**：同一个问题，带不带 history、history 顺序对不对，答案应该不同；
3. **模型维度**：换模型版本（deepseek-chat 升级）需要重新跑评估集；
4. **成本维度**：token 用量、时延，是"质量"的一部分（用户等 30 秒等于不可用）。
