# 第 6 章 接口层测试：pytest + requests 测 /chat

> 本章目标：搭起第一套可重复运行的接口测试，并亲历两次"红灯"——
> 一次是计划内的（空输入缺陷），一次是计划外抓出来的**真实 P0 bug**（SSE 流截断）。

## 1. 测试架构的三个设计决策

| 决策 | 做法 | 为什么 |
|---|---|---|
| 真服务器 | conftest 用 subprocess 拉起 uvicorn，测试走真实 HTTP | 接口测试测的是"网络上的契约"：序列化、header、状态码都得是真的 |
| 异常分支不 mock | 起第二台"坏 Key 服务器"（端口8124，Key=sk-invalid） | 上游必然 401 → 真实触发我们的 502 分支，比 mock 可信且免费 |
| 成本分层 | L1 单元零调用；真实调用只留 6 条必要用例；答案用 module 级 fixture 复用 | 一次全套 ≈ 6 次调用，成本不到一分钱；回归可天天跑 |

```
tests/
├── PLAN.md                      ← 第5章：测试计划
├── conftest.py                  ← 两个服务器 fixture：base_url / badkey_base_url
└── test_api/
    ├── test_unit_payload.py     ← L1：build_payload 拼装与裁剪（5条，全A级断言，0成本）
    ├── test_chat_api.py         ← L2：契约/校验/502/上下文/边界（8条）
    └── test_stream_api.py       ← 流式：SSE解析与协议完整性（3条）
```

## 2. 新概念逐个讲（配例子）

### pytest 基础三件套
- **fixture**：用例的"前置准备"。`base_url` 是 session 级——整套测试只起一次服务器；
  `normal_answer` 是 module 级——一次真实调用，两条用例复用断言（省钱关键技巧）。
- **断言就用 `assert`**：pytest 自动把失败原因打印成"期望 vs 实际"（你已见过）。
- **命名即文档**：`test_empty_message_should_be_rejected` 失败时，测试报告直接就是缺陷描述。

### L1 单元测试：把"最确定的部分"锁死
`build_payload()` 是纯函数：输入 history 12 条 → 输出必然是 system + 最后10条 + 本轮user。
**完全确定，所以全部 A 级断言（==）**。这层绿了，L2 出问题就能排除"拼装逻辑错"。
边界值用例 `test_exactly_max_history_not_trimmed` 正好卡在 MAX_HISTORY=10 的线上——
第 5 章说的"边界值对象变了"就是这里：边界不再是数字大小，而是**裁剪线、窗口线**。

### 流式接口的断言方式（第5章预言兑现）
`resp.json()` 失效。正确姿势：`requests.post(stream=True)` + `iter_lines()` 逐行取
`data: {...}`，把 delta **拼接还原成全文**再断言内容；同时断言协议完整性：
- content-type 是 `text/event-stream`
- 分块数 ≥ 2（防"假流式"：一次憋完整段再切片）
- **最后一行必须是 `data: [DONE]`**

### 502 用例的巧思
不起 mock 服务，而是让第二台服务器带着无效 Key 运行。上游返回 401，
`chat()` 里 `if resp.status_code != 200: raise HTTPException(502)` 被真实执行。
**用真实链路触发异常分支**，是接口测试比 mock 更硬核的地方（mock 的取舍在第 9 章细讲）。

## 3. 本章高潮：两次红灯的故事

### 红灯 #1（计划内）：空输入 → 修复 → 0.62 秒变绿
第 3 章发现的缺陷，写成用例 `test_empty_message_should_be_rejected`，首跑即红。
修复只改一行：`message: str = Field(min_length=1)`。
变绿后注意耗时：**0.62s**——空请求被挡在 pydantic，不再打到大模型。
**修复的收益肉眼可见：更快、更省钱。** 这就是"测试驱动修复"的完整闭环。

### 红灯 #2（计划外）：SSE 流截断——测试抓出的真实 P0
最终跑流式用例时炸出 `ChunkedEncodingError: Response ended prematurely`。

根因：DeepSeek 流的最后一行是 `data: [DONE]`，我们的代码对它执行
`json.loads("[DONE]")` → **异常，生成器当场死亡** → 流被掐断，我们自己约定的
[DONE] 永远发不出去。而 HTTP 状态码早在推流第一块时就锁定 200——**错误完全静默**。

为什么第 4 章人工验证没发现？当时用 `head -c 240` 只看了流开头。
**人肉测试看开头，自动化测试断言结尾**——协议完整性断言（"最后一行必须是[DONE]"）
就是为这类 bug 而生的。这正是测试计划 R7 风险的现实版。

修复：循环里先判断 `payload_str == "[DONE]"` 则 break，再对 JSON 块做 loads。

### 两次红灯的启示
| | 红灯#1 | 红灯#2 |
|---|---|---|
| 来源 | 已知缺陷，用例验证 | **测试主动发现** |
| 人工测试能发现吗 | 能（第3章就发现了） | 不能（只看开头会漏） |
| 说明 | 用例是"记忆的载体" | **用例是"探测器"** |

## 4. 最终结果

```
16 passed in 6.73s   （首跑：1 failed → 修复 → 全绿；流式2 failed → 修复 → 全绿）
```

## 6. 代码逐方法解析（本章代码的完整导读）

### 6.0 先记 pytest 的三条隐含规则
| 规则 | 本项目体现 |
|---|---|
| 文件名必须 `test_*.py` | `test_chat_api.py` 等 |
| 函数名必须 `test_` 开头 | 否则不被收集为用例 |
| 断言用 `assert` | pytest 自动渲染"期望 vs 实际" |

`conftest.py` 是**自动加载**的：无需 import，同目录测试可直接使用其中 fixture。

### 6.1 conftest.py：搭"测试舞台"的 4 个方法

**`ROOT`（模块级常量）**
`os.path.dirname(os.path.dirname(os.path.abspath(__file__)))`
= `/workspace/tests/conftest.py` → 去文件名 → 去一层 = `/workspace`。
用途：`cwd=ROOT` 保证子进程在项目根启动，`app.main:app` 才 import 得到。

**`_start(port, api_key) -> Popen`**
以子进程启动一台真 uvicorn 服务器并返回句柄。三个细节：
- `sys.executable`：用当前解释器，避免多版本 Python 混用；
- `env=env` 注入 Key：让同一份代码跑出"真 Key / 坏 Key"两幅面孔；
- `stdout/stderr=DEVNULL`：服务器日志不污染测试输出。

**`_wait_ready(base, timeout=20)`**
轮询 `GET /` 直到 200。`Popen` 只负责拉起进程，服务能接请求还要几百毫秒；
不等就发请求 → ConnectionError → **flaky（随机失败）**。所有"自起服务"的测试必做此步。

**`base_url` / `badkey_base_url`（fixture）**
```python
p = _start(...); _wait_ready(...)
yield GOOD_BASE      # 前=setup，值=注入用例，后=teardown
p.terminate()
```
作用：**依赖注入 + 生命周期管理**。`scope="session"` = 整个会话只起一次服务器
（否则 16 条用例起 16 次，每次约 2 秒）。两者差别只在 Key：好 Key 测正常路径，坏 Key 测故障路径。
用例只要写 `def test_x(base_url)` 即可自动获得地址。

### 6.2 test_unit_payload.py：L1 单元测试（5 条）

- **`make_history(n)`**：测试数据工厂，生成带序号的假历史，避免复制粘贴，且序号让断言能精确定位"第几条被裁掉"。
- **`class TestBuildPayload`**：纯命名空间，便于 `-k TestBuildPayload` 单独跑与报告归类。

| 用例 | 守的契约 |
|---|---|
| `test_messages_order_system_first_user_last` | 顺序：system 最前、本轮问题最后（顺序错模型会"认错人"） |
| `test_history_appended_in_order` | 历史保序，精确到下标 `msgs[1]`/`msgs[3]` |
| `test_history_trimmed_to_max` | 滑动窗口生效：12 条留后 10 条，`msgs[1]=="第2问"` 是算出来的（`[-10:]` 从原第 2 条起） |
| `test_exactly_max_history_not_trimmed` | 边界值：正好 10 条一条不裁，防 off-by-one（`>` 与 `>=` 之差） |
| `test_fixed_params` | 配置回归保护：temperature/max_tokens/model/stream=True 位；价值在"有人手滑改参数立刻红" |

全层用 `==` 精确断言，因为 `build_payload` 是纯函数：输入定 → 输出定。
这是第 5 章"隔离确定性、精确测"的第一块落地。

### 6.3 test_chat_api.py：L2 接口测试（8 条）

**为何用真实 HTTP 而非 TestClient**：TestClient 进程内直接调函数，绕过序列化、header、真实状态码；
接口测试的价值恰在"网络上的契约"。

**校验三兄弟**：
- `test_missing_message_field_returns_422`：除状态码外还断言 `"message" in r.text`
  ——不仅"拒了"，还要"拒得能看懂"（错误信息指出是哪个字段）。
- `test_message_wrong_type_returns_422`：`{"message":123}` 验证类型校验。
- `test_empty_message_should_be_rejected`：本章主角。断言写 `in (400, 422)` 而非 `== 422`
  ——**约束行为，不锁死实现**；换一种同样正确的拒绝方式不该误报。

**`test_upstream_failure_returns_502`**：用坏 Key 服务器真实触发上游 401 → 我们转 502。
额外断言 `"detail" in r.json()`，因为前端要靠它显示错误原因。

**`normal_answer`（module 级 fixture）**：一次真实调用喂两条用例。两个收益：
省钱；减少 flaky（两次分别调用可能一次含"退款"一次不含，断言口径不一致）。

**真实调用三用例**：
- `test_normal_question_structure`：B 级三段（非空 / 长度<3000 防抽风 / usage.total_tokens>0）。
- `test_normal_question_business_relevance`：`any(...)` 命中业务词。用 any 不用 all——
  模型措辞自由，命中一个就证明"在说退款"。
- `test_context_followup`：构造 history 后问"那运费谁出？"，断言含"运费/承担/报销/垫付"之一
  → 证明真读懂了上下文（R5 行为级验证）。**注意：这类断言有误报风险，B 级可接受，
  这也正是第 8 章要引入语义评估的原因。**
- `test_long_input_no_crash`：`"退款"*1000`（2000字），断言 `!= 500`。
  **反向断言/黑名单法**：想不到"正确答案"时，就断言"绝不允许出现什么"。

### 6.4 test_stream_api.py：流式（1 解析器 + 3 条）

**`parse_sse(resp) -> (全文, 是否DONE, 分块数)`**
手写 SSE 解码器。逐行读流 → 只要 `data: ` 前缀 → 特判 `[DONE]`（**它不是 JSON，
不能 loads**）→ 其余取 `delta` 拼起来。三个返回值各有用途：全文做内容断言、
got_done 做协议完整性、分块数证明"真流式"。

> **绝妙对称**：这个解析器一开始就正确处理 `[DONE]`，而被测代码当时是错的。
> **测试比实现更懂协议 → 于是抓出了那个 SSE 截断 P0。**

| 用例 | 作用与巧思 |
|---|---|
| `test_stream_is_sse_and_reassembles` | 7 断言四层：200 / content-type / 必须[DONE] / 非空 / **分块≥2 排"假流式"** / 业务词 / 耗时宽松界 |
| `test_stream_upstream_failure_returns_502` | 推流未开始就失败能返 502；同时揭示边界：推流开始后状态码锁 200，中途失败测不到（R7） |
| `test_stream_no_done_sentinel_would_fail` | 断言 `raw_lines[-1] == "data: [DONE]"`；用原始行而非解析结果，因为要验的是"**最后一行**"的位置 |

### 6.5 协作链
```
pytest 收集 test_* 函数
  → 发现参数 base_url → 去 conftest 找 fixture
      → _start() → _wait_ready() → yield 地址
  → 发现参数 normal_answer → 先满足其依赖 base_url
      → 调一次 /chat → 返回 JSON → 两条用例共享
  → 会话结束 → fixture yield 之后 → terminate 服务器
```

### 6.6 常用命令
```bash
pytest tests -v                    # 全部，详细
pytest tests -k stream             # 只跑名字含 stream 的
pytest tests/test_api/test_unit_payload.py::TestBuildPayload::test_history_trimmed_to_max
pytest tests -x --tb=short         # 遇错即停
pytest tests -q --durations=5      # 最慢 5 条
```

### 6.7 可迁移的 7 条设计原则
1. 数据工厂（`make_history`）：造数据不复制粘贴
2. fixture 作用域：贵资源 session、共享答案 module
3. 一次调用多断言：省钱 + 减 flaky
4. 不锁死实现（`in (400,422)`）：约束行为不约束写法
5. 反向断言：想不出正确答案就断言"绝不允许出现什么"
6. 协议完整性断言（`[DONE]`）：流/消息类接口必备
7. 断言级别标注（A/B/C）：一眼区分"真 bug"还是"措辞不同"

## 追问记录

### Q1：第 6 章写得太简单，需要解析代码——每个方法在本章起什么作用？

**答**：见上方"6. 代码逐方法解析"。要点速记：
- `conftest.py` 4 个方法 = 造舞台：`ROOT` 定位项目根、`_start` 起子进程服务器、
  `_wait_ready` 消除启动竞态（防 flaky）、两个 fixture 做依赖注入+生命周期管理（session 级只起一次）。
- `test_unit_payload.py` 5 条 = 锁死纯函数契约：顺序 / 保序 / 裁剪 / 边界不裁 / 参数回归。
- `test_chat_api.py` 8 条 = 门禁(422) + 空输入先红后绿 + 上游502 + 结构/业务词/上下文/不许500。
- `test_stream_api.py` = `parse_sse` 手写解码器（正确特判 [DONE]，故能抓出实现 bug）+ 协议完整性/假流式/哨兵位置三条。
