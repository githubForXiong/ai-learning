# 第 4 章 让客服"像样"：多轮上下文、人设与安全边界

> 本章目标：给客服加上"记忆"和"分寸"，并引入流式输出。
> 这两样也是第二部分最容易踩坑的地方——本章埋的坑，第 6/7/8 章逐个踩。

## 1. 三个新概念（配例子）

### 多轮上下文（大模型其实"失忆"）
反直觉的第一件事：**大模型本身没有任何记忆**。每次调用都是"初次见面"。
那为什么它能记住上文？因为**我们把历史对话重新拼进 messages 数组，每次一起发过去**。

```
第2轮请求的 messages =
  [system人设,
   {user: 我买的鞋子开胶了},      ← 上一轮用户说的
   {assistant: 可以申请退款或换货}, ← 上一轮AI答的
   {user: 那运费谁出？}]           ← 本轮新问的
```

正因为要"手动带历史"，才引出两个工程问题：
1. **谁来存历史？** 本项目让**前端存**（`history` 数组），每次随请求发给后端。
2. **历史太长怎么办？** 撞上第 2 章 Q1 说的 64K 窗口 → 用**滑动窗口**只带最近 N 条
   （代码里 `MAX_HISTORY = 10`，`history[-10:]`）。

### system prompt 人设与安全边界
人设不是"你叫小D"这么虚，而是**可执行的规则清单**。本项目写了三条：
1. 只答售后（退款/换货/物流/质量）；
2. 无关话题礼貌拒绝并引导回售后；
3. **不编造公司政策，不确定就转人工**。

第 3 条专门防第 1 章讲的"幻觉"——宁可说"帮您转人工"，也不瞎编一个退款时效。
**人设即配置，配置即测试对象**：第 8 章会把"该拒的拒没拒、该转人工转没转"做成评估用例。

### 流式输出（SSE）
默认大模型"憋整段"再返回，用户要干等。流式（stream=true）让模型**边生成边吐字**，
通过 **SSE（Server-Sent Events）** 协议一段段推给前端，实现打字机效果。
本项目新增 `POST /chat/stream`，每块长这样：
```
data: {"delta": "退款"}

data: {"delta": "到"}
...
data: [DONE]
```

## 2. 本章代码改了什么

- `build_payload()`：统一拼装 `人设 + 裁剪后的history + 本轮message`，`/chat` 和 `/chat/stream` 共用。
- `/chat`（保留非流式）：第 6 章接口测试的靶子，**故意不动它**，避免测试靶子乱飘。
- `/chat/stream`（新增流式）：返回 `StreamingResponse`，`media_type="text/event-stream"`。
- 前端：`history` 数组自己攒；`resp.body.getReader()` 读流、按 `\n\n` 切 SSE 块、逐字追加。

## 3. 实跑验证（本章验收）

| 能力 | 输入 | 实际输出 | 结论 |
|---|---|---|---|
| 上下文记忆 | 第2轮只问"那运费谁出？" | "质量问题导致的退换货运费由我们承担…" | ✅ 正确关联"鞋子退换" |
| 人设拒答 | "推荐几部好看的电影" | "抱歉，我主要负责售后…无法推荐电影" | ✅ 拒绝并拉回 |
| 流式输出 | "退款要几天到账" | `data:{"delta":"退款"}`…逐块 | ✅ SSE 分块正常 |

## 4. 埋下的三个测试坑（第二部分的主角）

1. **上下文依赖 → 测试要构造 history**：单问"那运费谁出"没有意义，
   接口测试必须会"带上下文"发请求，并断言回答**引用了上文实体**。这是 AI 测试用例设计的新维度。
2. **人设是"软断言"**：拒答、转人工这类"该不该"没有精确字符串可比，
   引出第 8 章的 LLM-as-Judge（用另一个模型打分）。
3. **流式让传统断言失效**：`/chat` 能一次拿到完整 `reply` 直接断言；
   `/chat/stream` 是碎片流，第 7 章 E2E 要处理"边流边等、流完再断言"的时序问题。
